## Remaining findings: severity, reachability and practical impact
1. **`zod` 3.25.76: high. Development tooling only; not in the app.**
   - Used only by `@expo/cli` (the dev server, export and prebuild commands). Even the newest `@expo/cli` (SDK 58,
     58.1.17) pins `zod ^3.25.76`, and the fix is in `zod` 4.6.6 (a major version with a different API). An override
     to 4.x would be an unsupported combination that could break the CLI.
   - `npm audit --omit=dev` still counts it, because `expo` is a runtime dependency and `@expo/cli` sits under it.
   - **Reachability:** the CLI validates the developer's own project config and local requests on the developer's
     machine. The exported Android and iOS bundles contain no zod code (no `ZodError` string).
   - **Practical impact:** low. At worst, the dev tool runs out of memory on input the developer already controls. No
     user data and no shipped app code are involved.
   - **Path to a fix:** an Expo CLI release that moves to zod ≥ 4.6.6.
2. **`decode-uri-component` 0.2.2 (via `query-string` 7.1.3, via `expo-router`): moderate. Reachable in the app at
   runtime.**
   - `expo-router` parses URLs with `query-string` (`getStateFromPath`), and the exported bundles include it.
   - Fixed versions (0.5.x) exist, but they are ESM-only (`"type": "module"`), while `query-string` 7.1.3 is CommonJS
     and requires `^0.2.2`, which has no patched release. Forcing 0.5.x would be an unsupported combination. `npm`
     offers the fix only with `expo-router` 58.0.28, which belongs to Expo SDK 58 (a major upgrade, out of scope).
   - **Practical impact:** low to moderate. A crafted deep link (`repone://…` or an Expo Go URL) with malformed
     percent-encoding could stall the app's JS thread on that device: a local denial of service while the link is
     handled. It exposes no data. The app has no server, and the user has to open the link.
   - **Path to a fix:** the SDK 58 upgrade (a separate, owner-approved task).
3. **`deepmerge` 4.3.1: low. Development and test tooling only.**
   - Used by `@expo/config` to load the app config, and by `jest-config`. The advisory covers every published version
     (`>=4.2.0 <=4.3.1`), so no fixed version exists.
   - Inputs are the project's own config files. It is not in the app bundle.
   - **Practical impact:** negligible.
   - **Path to a fix:** a patched `deepmerge`, or upstreams dropping it.

The 19 remaining `npm audit` entries are these three advisories plus the packages on their paths:

SDK 58 upgrade. All are rejected.

## Known limitations / risks
- **Needs a short Expo Go check on a device.** The JS side of `react-native-gesture-handler` (3.4.0) and
  `react-native-worklets` (0.13.1) moved by a minor and a patch version. npm's own resolution of `expo-router`'s `*`
  peers did that; it is not required for security.
- **Pre-existing, not caused here:** Expo Go for SDK 57 bundles native gesture-handler ~2.32.0, reanimated 4.5.1 and
  worklets 0.10.1, while `main` already resolves 3.3.0, 4.7.1 and 0.13.0 through `expo-router`'s peers.
  `expo-modules-core` declares worklets `^0.7.4 … ^0.10.0`, and `npm ls` flags 0.13.x as invalid, both before and
  after. The app has worked in Expo Go with these versions. Aligning them is a separate task, not part of this
  security fix.
- **`xcode` 4 is exercised only by native prebuild and EAS builds,** which this project does not run yet; Expo Go
  does not use it. It is Expo's own pairing, which lowers the risk.
- **After merging, `npm ci` re-downloads Expo packages on each machine.** On the owner's Windows laptop, the
  `lightningcss` Windows binary is now in the lockfile.
